# Scope Creep Guard

> Основа PRD: `idea-006-scope-creep-guard-2026-05-25.md`. Рыночные показатели и характеристики пользователей из исходного документа считаются гипотезами до проверки на реальных пользователях.

## 1. Контекст и проблема

Фрилансеры и небольшие агентства регулярно получают от клиентов дополнительные запросы, которые могут выходить за рамки согласованных работ. Пользователю приходится вручную сравнивать запрос с договорённостями и решать, нужно ли просить дополнительную оплату.

Особенно сложно фрилансерам, для которых английский язык не родной: они могут соглашаться на бесплатную работу из-за страха прозвучать грубо или испортить отношения с клиентом.

**Подтверждено исходным документом:**

- продукт должен сравнивать новый запрос с исходным scope;
- результат должен включать вердикт и профессиональный ответ клиенту;
- запросы часто поступают через Upwork и Gmail;
- для анализа необходимо хранить исходный scope проекта.

**Гипотезы, требующие проверки:**

- пользователи теряют на неоплачиваемом расширении scope от `$1 000` до `$5 000` в месяц;
- 78% пользователей не выставляют счёт за дополнительную работу;
- анализ вручную занимает 30–60 минут;
- пользователи готовы платить `$15–30` в месяц;
- наибольшую боль испытывают non-native English фрилансеры.

## 2. Цель первой версии

Создать рабочий прототип, который позволяет менее чем за две минуты:

1. Сохранить исходный scope проекта.
2. Добавить новый запрос клиента.
3. Определить, входит ли запрос в scope.
4. Объяснить вердикт.
5. Подготовить вежливый ответ клиенту.
6. При необходимости сформировать простой Change Order.

Первая версия должна проверить главную гипотезу: помогает ли такой анализ пользователю обнаруживать неоплачиваемую работу и увереннее обсуждать дополнительную оплату.

## 3. Целевая аудитория

### Основной пользователь

Индивидуальный фрилансер, который:

- работает с зарубежными клиентами;
- ведёт переписку на английском языке;
- получает запросы через Upwork, Gmail или другие браузерные каналы;
- работает в разработке, дизайне или маркетинге;
- самостоятельно согласует объём и стоимость работ.

Пользователь одновременно является предполагаемым покупателем продукта.

### Вторичная аудитория

Владельцы и сотрудники небольших агентств, контролирующие объём клиентских работ.

Выбор индивидуального фрилансера как главного пользователя первой версии является предположением и требует подтверждения.

## 4. Пользовательский сценарий

1. Пользователь создаёт проект.
2. Указывает свою роль и отрасль.
3. Вставляет исходный scope или загружает договор/SOW.
4. Получает новый запрос клиента.
5. Вставляет запрос вручную либо передаёт выделенный текст через расширение.
6. Система сравнивает запрос с исходным scope.
7. Пользователь получает один из вердиктов:
   - `In scope`;
   - `Borderline`;
   - `Out of scope`.
8. Система показывает краткое объяснение со ссылкой на соответствующие части scope.
9. Система генерирует профессиональный ответ на английском языке.
10. Для `Out of scope` пользователь может создать Change Order.
11. Пользователь редактирует результат, копирует его и отправляет клиенту.
12. Проверка сохраняется в истории проекта.

Ключевой момент ценности: пользователь впервые обнаруживает запрос вне scope и получает готовый ответ для обсуждения дополнительной оплаты.

## 5. Функциональные требования

### Обязательные

**FR-1. Управление проектами**

- Пользователь может создать проект.
- Для проекта сохраняются название, отрасль и исходный scope.
- Пользователь может выбрать существующий проект перед анализом.

**FR-2. Добавление scope**

- Scope можно вставить как обычный текст.
- Прототип должен хранить scope между сессиями.
- Загрузка файлов договора или SOW желательна, но может быть ограничена одним-двумя форматами.

**FR-3. Добавление запроса**

- Пользователь может вставить текст запроса вручную.
- Если в прототип входит Chrome Extension, оно передаёт выделенный текст в форму анализа.

**FR-4. Анализ**

- Система сравнивает запрос только с выбранным scope.
- Система выдаёт один из трёх вердиктов.
- Вместе с вердиктом показывается простое объяснение.
- Неуверенный результат должен обозначаться как `Borderline`, а не выдаваться за точное решение.

**FR-5. Ответ клиенту**

- Система генерирует вежливый ответ на английском языке.
- Ответ можно отредактировать и скопировать.
- Текст не должен автоматически отправляться клиенту.

**FR-6. Change Order**

- Для запроса вне scope можно сформировать простой Change Order.
- Документ содержит описание дополнительной работы и поля для стоимости и сроков.
- Пользователь проверяет документ перед отправкой.

**FR-7. История**

- Система сохраняет выполненные проверки и созданные Change Orders внутри проекта.
- Для прототипа достаточно простого списка без поиска и аналитики.

**FR-8. Безопасность**

- Данные одного пользователя не должны быть доступны другому.
- Перед отправкой данных в LLM пользователь должен понимать, какие материалы обрабатываются.
- Нельзя заявлять о полной NDA-безопасности до проверки архитектуры хранения и обработки данных.

### Желательные, если остаётся время

- загрузка PDF/DOCX;
- переключение тона ответа;
- указание предлагаемой стоимости дополнительных работ;
- оценка сэкономленной суммы после проверки;
- простая обратная связь: согласен ли пользователь с вердиктом.

## 6. Что не входит в первую версию

- автоматический импорт проектов из Upwork;
- чтение всей переписки пользователя;
- автоматическая отправка ответа клиенту;
- интеграции с HoneyBook, Bonsai и другими CRM;
- полноценная система управления договорами;
- API для сторонних продуктов;
- обучение персональному стилю пользователя на большой истории;
- сложная отраслевая калибровка;
- совместная работа команды и управление ролями;
- юридически значимая электронная подпись;
- гарантия юридической силы Change Order;
- поддержка требований всех стран и юрисдикций;
- мобильное приложение;
- биллинг и несколько тарифов, если они не нужны для тестирования спроса.

## 7. Ограничения и допущения

### Ограничения

- Граница между уточнением и расширением scope субъективна.
- Качество результата зависит от полноты исходного scope.
- Договоры и переписка могут содержать конфиденциальные данные.
- LLM может ошибочно классифицировать запрос или придумать отсутствующее условие.
- Change Order не является юридической консультацией.

### Допущения

- Для первого теста достаточно английского языка.
- Пользователь готов вручную вставить scope и новый запрос.
- Один выбранный проект предоставляет достаточно контекста для анализа.
- Результат всегда проверяется пользователем перед отправкой.
- На старте можно поддерживать разработку, дизайн и маркетинг без глубокой специализации.
- Chrome Extension и Web SaaS названы целевой формой продукта, но необходимость создавать оба интерфейса одновременно ещё не подтверждена.

## 8. Критерии готовности

### Готовность к демонстрации

Прототип готов к показу, если:

- пользователь может пройти основной сценарий без помощи разработчика;
- scope сохраняется и повторно используется;
- запрос получает вердикт, объяснение и готовый ответ;
- обработка обычно занимает менее двух минут;
- система корректно сообщает о неопределённости;
- ответ можно отредактировать и скопировать;
- для `Out of scope` создаётся простой Change Order;
- критические данные не видны другим пользователям;
- ошибки не приводят к потере введённого scope.

### Признаки полезности

- Не менее пяти тестовых пользователей прошли основной сценарий.
- Пользователи понимают вердикт без дополнительных объяснений.
- Хотя бы пять пользователей за первые 30 дней задокументировали обнаруженную неоплачиваемую работу или сохранённые деньги.
- Пользователи сообщают, что готовый ответ повысил уверенность в разговоре с клиентом.
- Отслеживаются:
  - число проверок scope в неделю;
  - доля результатов `Out of scope`;
  - число созданных и отправленных Change Orders;
  - самостоятельно указанная сэкономленная сумма;
  - возврат пользователей на четвёртой неделе.

Порог «пять пользователей» взят из исходной kill-метрики и остаётся продуктовой гипотезой.

## 9. Открытые вопросы и риски

### Открытые вопросы

- Кто должен быть первым сегментом: разработчики, дизайнеры или маркетологи?
- Нужен ли Chrome Extension для проверки гипотезы или достаточно веб-прототипа?
- Какой способ добавления scope удобнее: текст, файл или импорт?
- Как объяснять вердикт так, чтобы пользователь мог ему доверять?
- Как пользователь должен исправлять ошибочный вердикт?
- Нужна ли цена и новый срок внутри первой версии Change Order?
- Какие данные допустимо передавать внешнему LLM?
- Нужно ли локальное хранение для проектов под NDA?
- Как измерять реальные, а не предполагаемые сэкономленные деньги?
- В каких юрисдикциях Change Order может использоваться без подписи?
- Подтверждается ли готовность платить `$15–30` в месяц?

### Основные риски

- Ошибочный вердикт может повредить отношениям с клиентом.
- Пользователь может принять AI-ответ за юридическую рекомендацию.
- Недостаточно подробный scope снизит качество анализа.
- Работа с конфиденциальными документами может ограничить использование продукта.
- Пользователи могут считать проблему важной, но решать её слишком редко для подписки.
- Одновременная разработка расширения и веб-приложения может замедлить проверку гипотезы.

## Следующий шаг для сборки прототипа

Собрать кликабельный веб-прототип одного сценария: `scope → новый запрос → вердикт → объяснение → ответ → Change Order`. Проверить его на 5–10 фрилансерах с реальными обезличенными примерами. Решение о Chrome Extension принимать после этих тестов.
