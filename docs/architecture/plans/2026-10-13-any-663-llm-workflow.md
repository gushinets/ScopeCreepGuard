## 2. Execution ownership, discovery, and recovery

**Owner:** Add `LlmWorker` as a backend service. Extend the existing `apps/worker/main.py` composition entrypoint with `SCOPE_GUARD_WORKER_ROLE=llm` (default remains export), reuse the existing worker image, database/UoW lifecycle, process supervision, and PostgreSQL claim/fencing pattern. Run a separate LLM worker service from the rollout overlay; LLM mode requires provider configuration and PostgreSQL, not an export bucket. Preserve the existing export worker role. Do not put model work in FastAPI request tasks, an in-memory-only queue, or the operation-status GET.

- An authenticated POST validates/admit-checks the command and commits the operation, frozen inputs/references, policy snapshot, and stage rows in a short transaction before returning `202`. A disconnect after that commit only stops the HTTP response; it does not cancel the operation. Remove `run_connected` ownership of generation execution. If admission rolls back before commit, no operation exists; redelivery with the same command key is safe.
- The worker scans at startup and every two seconds. Reconcile expired/abandoned rows first, then claim eligible queued operations or running operations with expired leases using `FOR UPDATE SKIP LOCKED`, ordered by creation time and ID. Default concurrency is one operation per LLM worker, with the two post-analysis stages concurrent within that operation. Persisted rows are the queue; notifications may reduce latency but are not required for recovery.
- Claim and commit a monotonically increasing fencing epoch, worker identity, and a 90-second lease. Renew every 15 seconds using the matching epoch, running status, unexpired lease, and original absolute deadline. Use database time. A failed renewal cancels the operation's local stage tasks and prohibits further dispatch, accepted-stage writes, or publication; do not let a failed heartbeat merely exit its own task.
- Before every dispatch and accepted-stage/publication write, enforce the epoch, live lease, deadline, and persisted budgets. Concurrent reply/CO calls reserve counters and money under the same operation lock. Accepted stage outputs are immutable. A stale executor cannot replace them, publish, or apply a Draft revision.
- On restart/reclaim, load frozen inputs, prompt/schema/model/policy versions, accepted stages, semantic counters, and private stage checkpoints. Skip accepted stages. Resume only unfinished stages, reconstructing their validation feedback and using their remaining corrective allowance; do not reset retry counters, deadline, or money reservations. If a pinned implementation/version is unavailable, fail explicitly rather than use current project/configuration values.
- Checkpoints identify a prepared semantic request, its consumed/remaining transport indices, and any returned candidate JSON awaiting validation. Persist the candidate in the protected stage checkpoint alongside call completion before returning it to PydanticAI. Revalidate an unaccepted stored candidate locally with the same typed/domain validators rather than paying for its regeneration. For an interrupted request with no candidate, resume only its remaining gateway transport allowance; transport exhaustion is a terminal stage failure, not an additional semantic retry. After a persisted validation failure, start the next semantic request with its saved feedback and calculate PydanticAI's new-run output retry allowance as `remaining_semantic_attempts - 1`; the persisted gateway counter remains the hard backstop.
- A call reserved but provably not dispatched can be released as `not_sent`. A dispatched/in-flight call abandoned on timeout, crash, lease loss, or shutdown becomes `unknown`; retain its worst-case reservation and consumed attempt. It may have executed externally. A permitted replacement attempt requires a separate reservation and remaining call/semantic/transport limits. No exactly-once external-execution claim.
- The reconciliation pass terminally fails expired operations and those needing another attempt without remaining budget. If all stages are accepted, call exhaustion alone does not block assembly/publication while the deadline is still valid. Publication failure rolls back only publication; accepted outputs and provider accounting survive and can be republished idempotently within the deadline.
- SIGTERM/SIGINT stops claims. Allow active work up to the smaller of 30 seconds or its remaining deadline, then cancel local tasks and perform bounded, shielded accounting cleanup. Stop lease renewal during final shutdown and leave unfinished work recoverable after expiry. If PostgreSQL is unavailable, the already committed in-flight row/reservation is the recovery evidence; do not claim cleanup succeeded. Configure container shutdown grace to exceed the worker's drain/cleanup allowance.
- No new cancel UI/endpoint is required. Internal cancellation comes from deadline, lease loss, shutdown, and transport timeout; those reasons remain distinct. New requests/edits do not cancel a historical operation automatically. Its accepted result can enter History but must not overwrite the newer Draft.
- Late provider usage/IDs/cost may update that call's own accounting record after fencing loss, idempotently by call ID. This accounting-only path cannot accept a stage, change execution ownership, reactivate an operation, or publish content. Preserve uncertain reservations until reconciliation provides reliable usage/cost evidence.

## 3. Concrete PydanticAI-to-gateway bridge: first implementation gate

Implement `GatewayResponsesModel`, a custom subclass of PydanticAI 2.2.0 `Model`, in the existing LLM integration boundary. Its non-streaming `request(messages, model_settings, model_request_parameters) -> ModelResponse` delegates exclusively to `ProviderGateway.request(StageProviderRequest)`. A per-stage binding contains operation/stage IDs, fencing epoch, frozen policy, and semantic attempt allocation. No model tools, external tracing, or automatic provider fallback are enabled.

| Layer | Required handoff |
| --- | --- |
| PydanticAI runner | `Agent(model=GatewayResponsesModel(...), output_type=NativeOutput(StageOutput, strict=True), retries={"output": remaining_semantic_attempts - 1})`; typed outputs forbid extra fields. Initially three semantic attempts means two corrective retries; resumption uses the durable remaining allowance. Output validators raise `ModelRetry` containing field path, rule, expected/detected language, and confidence without changing accepted facts. |
| Custom model | Call `prepare_request`. Use a profile declaring native schema support and the pinned `OpenAIJsonSchemaTransformer`; reject unsupported output modes/tools. Read the prepared `output_object.json_schema`, name, and strictness from `ModelRequestParameters`, not a prompt-only schema string. |
| Messages and feedback | Serialize system instructions and user text, preceding same-stage JSON responses as assistant text, and `RetryPromptPart.model_response()` feedback in order into Responses input items. Do not drop the rejected response/feedback or include another check's history. Use no provider-side conversation or `previous_response_id` chaining. Persist only protected, operation-local corrective checkpoints; technical events never contain prompts/client messages. |
| Gateway | Allocate each semantic attempt durably; reserve/record each physical transport attempt. Derive model and reasoning effort from frozen server policy: medium for analysis/materials/estimate, high for regeneration. Every corrective request re-enters this same gateway and budget ledger. |
| LiteLLM adapter | Call `litellm.aresponses` with the prepared native schema in `text.format = {type: json_schema, name, strict: true, schema}`, Responses input, `reasoning={effort: ...}`, model, remaining timeout, and output-token cap. Use the pinned SDK's injected `AsyncHTTPHandler` over a no-retry HTTP client for transport reuse and wire interception; verify actual request count instead of assuming zero-valued retry options suffice. Disable LiteLLM/provider/http-client retries, schema/parameter-dropping fallbacks, and routing fallback. Never invoke a provider SDK directly around LiteLLM. |
| Response normalization | Capture actual model/provider when reported, usage (including cache/reasoning details), provider response/request IDs, LiteLLM response ID, latency, status, and sanitized errors in the call ledger before semantic acceptance. Return JSON text as `ModelResponse.parts=[TextPart(...)]`, with actual model/provider/response ID and mapped `RequestUsage`; mark missing usage explicitly in metadata. |

PydanticAI usage defaults/estimates must not become reported billing data: its numerical defaults may be zero when fields are missing, while SQL usage stays `NULL` with an unknown status. The gateway ledger is authoritative for physical calls and spend. Refusal/incomplete responses cannot become accepted stage objects. The same fixed schema and reasoning settings apply to each corrective attempt.

**Early gate, before worker/API/UI integration:** Add `backend/tests/unit/test_gateway_responses_bridge.py` using the real pinned PydanticAI and LiteLLM libraries, an in-memory ledger double, and an injected HTTP transport double. Inspect outbound HTTP bytes, not merely a mocked `aresponses` argument list. Prove:

1. NativeOutput's strict schema reaches the provider request intact (including required fields and `additionalProperties: false`); Unicode input and medium/high reasoning settings survive.
2. A wrong-language response with a correct language tag causes `ModelRetry`; the next physical request includes the concrete feedback and preceding rejected JSON, traverses the gateway, and preserves scope/numerical facts.
3. A subsequent retryable transport error is retried only by the gateway: one semantic correction plus one transport retry produces exactly three outbound HTTP requests and three ledger records with the expected indices. Exercise 422/schema errors too, to detect SDK-internal transformation retries or silent schema degradation.
4. Provider/model/IDs and reported usage reach PydanticAI and the ledger correctly; absent usage/cost stays unknown in the ledger; refused/incomplete output and exhausted retries fail explicitly.
5. New stage runs have fresh history; resumption retains accepted outputs and spends only remaining attempts.

Run this focused file with the backend's normal pinned test environment. Failure is a stop gate: resolve the adapter/SDK compatibility without weakening native schema or changing retry ownership before proceeding. Do not substitute the reference FunctionModel pattern without its own equivalent wire-level proof. Static inspection of that reference's FunctionModel showed automatic usage estimation when no usage exists, reinforcing the need for separate accounting; no runtime compatibility proof has been performed by this refinement.

## 4. Legacy API compatibility and asynchronous frontend transition

- All four legacy generation endpoints (`/api/analyze`, `/api/replies/regenerate`, `/api/client-materials/language`, `/api/change-orders/estimate`) become adapters to the same durable admission/worker pipeline. Explicitly allow only these adapters through the v2 workflow boundary; other unsafe legacy writers retain their existing upgrade-required behavior. Adapters must use current workflow repositories/owned legacy envelopes, not retired ORM columns or the old direct OpenAI service. There is no validation/persistence/budget bypass route.
- **Missing-key policy:** Require a UUID command key in the existing request body's `operationId` or `Idempotency-Key` header. If both are supplied, require equality. Omission returns `428 errors.operationRequired` before creating an operation or invoking a provider; inconsistent keys return `400`. The server does not mint a fresh key for an identifier-free generation request. This intentional compatibility change is documented in OpenAPI and the caller migration notes.
- Existing request-body `operationId` is the client command key; the returned operation-resource ID is separate. Persist uniqueness by owner/project/command key, with operation kind and canonical command parameters in the digest. Same key/hash returns the existing operation/outcome before current-revision validation; changed parameters/kind return `409`. A new deliberate check uses a new key even for identical text. Re-delivery of a terminal failure returns that failure; an explicit new attempt is a new command.
- The frontend allocates and persists the key with immutable command parameters before its first POST, scoped to the signed-in owner. Retain it and any returned operation-resource ID across network failure, `202`, navigation, and reload; never clear it on mere HTTP acknowledgement. Clear only after terminal acknowledgement or deliberate abandonment/new command, with owner/logout cleanup. The server echoes the supplied key and returns the resource ID; a lost POST response is recovered by re-sending the same keyed command. Extend the Next forwarder's request allowlist for `Idempotency-Key` and its response allowlist for the echoed header.
- The server resolves project, Draft/revision, historical analysis run, and owned legacy envelope references before freezing inputs. Regeneration/translation/estimate requires an owned persisted check source whose request/project binding matches. A verified server-issued proof may locate/bind that source but cannot replace database authority. Missing, foreign, mismatched, or unresolvable historical sources fail; do not fall back to today's scope. Legacy client `analysis`/snapshot payloads are not authoritative. Manual values for translation come from the owned persisted document revision; previous reply text is variation input only. Never reclassify a saved check during regeneration.
- For current commands, freeze the saved source Draft revision. Both v2 and activated legacy adapters require `expectedRevision`; omission is rejected, rather than capturing a different revision on redelivery. Unsupported legacy selectors/unsaved historical contexts return an explicit error rather than creating a fresh analysis. Retrying a command does not refreeze from a newer revision.
- New admitted generation POSTs return `202` with `{operationId, status, statusUrl, deadlineAt}`, `Location`, `Retry-After: 2`, and `Cache-Control: private, no-store`. Completed duplicate POSTs return the persisted original successful legacy/v2 envelope; failed duplicates return the stored terminal error/status. Existing successful result/reply/materials envelopes remain compatible.
- `GET /api/v2/llm-operations/{operationId}` performs an owner-filtered read only and returns stored status, deadline, stage statuses, terminal `result` (the original endpoint envelope), or sanitized terminal `error`/HTTP status. It does not claim, renew, recover, dispatch, or publish. Foreign IDs return `404`. A worker outage can leave persisted status pending until reconciliation; the client can stop waiting at the displayed absolute deadline, but polling does not mutate that row.
- Update both the durable client helper and remaining legacy generation callers to branch on `202` before parsing a successful generation envelope, poll every two seconds while mounted, unwrap only terminal results, and surface terminal errors. Reload resumes polling or re-delivers the saved key when the resource ID was lost. Keep loading/double-click protection and manual text intact. Browser disconnect stops polling only. API changes require generated-contract updates; unchanged result fields do not.

## 5. Frozen languages, semantic validation, and bounded accounting

### Language and content

- Summary, reasoning, and suggestion use interface language; all three replies and Change Order prose/labels use the frozen detected request language or explicit override. Language selection is bound to the request fingerprint. A new request invalidates the old override; a saved revision restores its own selection. A localized dropdown below client materials shows language names, selected default, and any detection uncertainty.
- Lingua's initial tunable thresholds are confidence >= 0.80, runner-up gap >= 0.20, and dominant classified prose >= 75%. Scores/thresholds are not established accuracy guarantees. Record detector/policy version and calibrate using customer fixtures plus short phrases, proper names, URLs, neutral strings/emoji/SEO, mixed languages, Spanish accents/questions and "Hola" followed by non-Spanish prose. Include other existing supported languages to avoid ES-specific branches.
- Input uncertainty uses an explicit override or the documented interface-language fallback, visibly marked as uncertain/fallback. The model cannot choose another target during correction. Output uncertainty is different: ignore only verified verbatim citations, known names, URLs, and identifiers; evaluate substantive fields/sentences independently and short labels with grouped evidence/known localized labels. Request correction or fail if generated prose still lacks adequate language evidence. Do not publish detected wrong-language or unresolved output as success, or silently switch its target to the interface language.
- Validate strict structure, complete independent replies, scope citations present verbatim in the frozen scope, accepted scope position, normalized numerical terms, currency, timeline commitments, and invented approvals/free-work promises. Translation preserves current saved manual commercial values as well as verdict/scope; existing estimate refresh can change estimates through its established rules only, without reclassifying scope or introducing pricing formulas. Add contradictions such as Arrow/email being "already included free" despite a historical out-of-scope result. These constraints/regressions reduce risk and do not prove every commercial contradiction detectable.
- Raise concrete field/rule errors through `ModelRetry` for the failed stage only. Persist accepted stages and private corrective state; no cross-check conversation history. Keep confirmation before replacing manual reply/CO text, and preserve it after failure or cancellation.

### Limits and unknown-cost admission

| Frozen policy default | Limit |
| --- | --- |
| Corrective retries | Two per stage, after one initial semantic attempt |
| Transport attempts | Two per semantic attempt, gateway-owned |
| Physical calls | 12/check, 8/translation, 6/regeneration, 6/estimate refresh |
| Deadline / call timeout | 180 seconds from admission; each call <= min(60 seconds, remaining time) |
| Prompt / output caps | 32,768 input tokens including schema/history/feedback; 4,096 output tokens including billed reasoning where supported |
| Money admission envelope | USD 1.00 per operation, configurable Decimal value frozen at admission |

- Before returning `202`, establish a safe per-call bound from either a versioned known tariff or an explicitly configured conservative maximum tariff for the allowed provider/model (including permitted actual-model aliases, cache/reasoning billing, validity period, and currency). Require supported token counting or a documented conservative input bound and a provider-enforced billed-output cap. If pricing, token accounting, provider behavior, or fixed fees cannot be safely bounded, refuse execution with `503 errors.providerBudgetUnavailable` and zero external calls. Persist a keyed terminal admission failure so repeated delivery is consistent; never treat absent pricing as free.
- Snapshot the chosen tariff/bound provenance in the operation policy; a bound must be valid through the operation deadline. Do not add a general pricing/billing subsystem. Unknown tariff admission is possible only with an operator-supplied conservative bound; if neither known rates nor such a bound exists, refuse. Native schema/reasoning support and retry suppression are also required capability checks; fail configuration clearly instead of silently dropping parameters.
- Before every physical dispatch, atomically reserve `upper_input_tokens * upper_input_rate + maximum_billed_output_tokens * upper_output_rate + any bounded fee`, allocate the call index, and commit the call row. Admit only if accumulated assessed spend plus all unresolved/concurrent reservations plus the new reservation fits the frozen money envelope and remaining call/time limits. A call may fail admission even when previously accepted stages exist; report failure without publishing partial client output.
- Keep `reported_cost` (provider-supplied), `estimated_cost` (Decimal calculation from reported usage and the frozen tariff), and `reserved_cost_upper_bound` distinct, with currency/source/status. Missing reported cost remains `NULL` even when an estimate exists; missing usage remains `NULL`. Do not copy LiteLLM/PydanticAI inferred zeros or estimates into reported fields. Cached/reasoning details that are subsets of input/output must not be double-counted.
- Use reliable reported cost when available, otherwise a reproducible tariff estimate only when requisite usage exists; retain the conservative reservation when actual cost remains unknown. Unknown/reserved expenditure is displayed separately from known totals, not added as a fabricated actual bill. Conservatively use the larger supported assessment when reported and estimated figures disagree; stop additional calls and record discrepancies if an observed amount exceeds the configured bound.
- Count every rejected model response and every transport attempt. Uncertain timeout/crash outcomes retain their full reservation and consume attempts; a retry reserves anew. Accounting-only late observations may reconcile a reservation with trustworthy cost/usage, but never erase an attempt or retrospectively authorize a stale output. Distinguish reserved/not-sent, confirmed dispatched/completed, and uncertain dispatches in measurements; do not claim an exact physical count where a crash left dispatch uncertain.
- This is conservative admission under explicit tariff/token/call assumptions, not a guarantee of the provider's ultimate invoice. A ceiling on known accumulated cost alone is explicitly insufficient. Unknown costs remain visible and can exhaust the budget through retained reservations.
